# SW-052 — Address/location candidate rescue experiment (evaluation only)

## Hypothesis

A company can change its name while keeping its street address and locality. The current candidate-engine-v0.4.0 name/location and name/address passes can miss this genuine cross-source pair when no other identifier agrees. A separate, bounded street-plus-locality candidate pass might rescue such pairs, but buildings shared by unrelated entities create dangerous extra candidates.

## Experiment contract

- **Baseline:** run unmodified product generate_candidates with the confirmed identity mappings.
- **Proposed pass:** index exact normalized **street + confirmed geography**. It deliberately does not depend on company-name overlap. Street and locality must both be nonempty. A/B mapping IDs must agree.
- **Bounds:** suppress a key entirely if either side exceeds the per-side cap or its cross-product exceeds the pair cap. Never select an arbitrary prefix of a large bucket.
- **Evaluation:** generate baseline/proposed pairs from visible data before introducing hidden known-true and known-hard-negative pair labels. Compare the union with the baseline; do not count a pair already generated by the baseline as a rescue.
- **Outputs:** candidate recall denominator and numerator, newly recovered truth, added candidate count, newly admitted *known* hard negatives, unlabeled added pairs, and suppressed keys/relationships. Unknown pairs must never be described as verified false matches.
- **No production behavior:** the experiment is in a separate matcher evaluation module and is not wired into product candidate generation, identity decisions, matching scores, API contracts, or export.

## Fixed synthetic microcase

Three known cross-source true pairs are constructed. Two have completely changed organization names while remaining at the same street/locality; a third is a normal unchanged-name control. Two unrelated organizations share the first street and form known hard-negative cross-pairs.

The tests assert the expected baseline and proposed pair sets. This is a **test fixture**, not evidence of population-level accuracy, calibrated confidence, or scalability. Exact same-address evidence alone is never sufficient to auto-confirm identity.

## Verification gates

Run:

    uv run --project services/matcher pytest services/matcher/tests/test_address_location_probe.py -q
    uv run --project services/matcher ruff check services/matcher/src/samewise_matcher/address_location_probe.py services/matcher/tests/test_address_location_probe.py
    uv run --project services/matcher ruff format --check services/matcher/src/samewise_matcher/address_location_probe.py services/matcher/tests/test_address_location_probe.py
    pnpm verify

The normal CI matcher benchmarks and synthetic browser acceptance must remain green. Because the probe is not activated in product matching, existing matcher snapshots should remain unchanged.

**Before considering a product blocker:** freeze independent 1K/10K+ adversarial fixtures with genuine renames, address reuse, incomplete geography, stale/moved addresses, and missing fields; measure candidate recall, incremental candidate volume, hard-negative admissions, bucket suppression, runtime, and memory against an unchanged v0.4.0 baseline. Evaluate larger datasets and scoring/one-to-one conflicts if initial results justify expansion. A later product change would require a new blocker ID and candidate-engine/config version, provenance, and fresh regression gates.

## Known limits

The probe does exact *normalized* address and locality equality, not geocoding. It may miss changed or incomplete addresses and may admit many unrelated organizations at a shared building. Mappings are assumed already human-confirmed. It deliberately makes no geographic equivalence or residential/business occupancy inference.
